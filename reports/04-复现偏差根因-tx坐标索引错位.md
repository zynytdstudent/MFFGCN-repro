# 04 — 复现偏差根因定位：发射机坐标索引错位

> 2026-11-04。这份文档推翻并作废了此前所有 run 的 val / test 数字。

## 一、一句话结论

`src/dataset.py` 里发射机位置图的坐标用了 **split 内的局部下标** 去索引 **全局的 `tx_coords.npy`**。
训练集因为恰好从全局第 0 行开始，局部下标 == 全局下标，所以训练一直是**对的**；
验证集和测试集拿到的是**随机的、错的发射机位置**。

模型在错的输入上被评估，于是出现"训练 RMSE 0.019 ≈ 论文 0.018，测试 0.066"的荒谬差距。
这不是模型问题，不是超参问题，也不是论文口径问题。

## 二、错误的代码

```python
# src/dataset.py  (修复前)
idx, city, txid = self.rows[i]          # idx = 全局行号, i = split 内下标
...
r, c = int(self.tx[i][0]), int(self.tx[i][1])   # ← 用 i 查全局表，错
```

`tx_coords.npy` 由 `prepare_data.py` 按全局顺序写出，第 k 行对应 `index.csv` 里 `idx=k` 的样本。
正确写法是 `self.tx[idx]`。

## 三、证据

### 3.1 发射机位置与真实信号峰值的距离

`prepare_data.py` 已记录：`argmax(gain map)` 就是发射机像素。以此做真值校验（每 split 抽 150 张）：

| split | 样本数 | `tx[i]` 到真实发射机平均距离 | `tx[idx]` 到真实发射机 |
|---|---|---|---|
| train | 40 000 | **0.00 px**（恰好正确） | 0.00 px |
| val | 8 000 | **76.4 px**（随机） | 0.00 px |
| test | 8 080 | **86.3 px**（随机） | 0.00 px |

256×256 的图上偏 76–86 像素，等于把一个随机点写成发射机。

### 3.2 训练集/测试集误差对比（`calib_single`，50 epoch，修复前）

| 集合 | NMSE | RMSE |
|---|---|---|
| 训练集（eval 模式） | 0.00714 | **0.01895** |
| 训练集（train 模式，排查 BN 假象） | 0.00711 | 0.01924 |
| 测试集（修复前） | 0.06367 | **0.06618** |

训练集 RMSE 0.0190 与论文 U-Net 的 0.0182 几乎相等 —— 模型早就学会了任务，
只是被喂错的坐标去评估。BN 模式与 eval 模式一致，排除"BN 统计量假象"。

进一步：测试集上**观测像素本身**的 RMSE 只有 0.0365（NMSE 0.019），而观测像素只占
全图 0.24%，却贡献了 0.24% 的能量 —— 说明模型连已知点都没拟合好，是输入矛盾而非欠拟合。

### 3.3 修复后只跑 5 个 epoch（`smokefix`）

| epoch | val NMSE | val RMSE |
|---|---|---|
| 1 | 0.0868 | 0.0541 |
| 2 | 0.0342 | 0.0340 |
| 3 | 0.0260 | 0.0296 |
| 4 | 0.2074 | 0.0837（偶发尖峰，见第五节） |
| 5 | 0.0182 | 0.0248 |

**测试集：NMSE 0.00877 / RMSE 0.02456**（修复前 50 epoch 是 0.0637 / 0.0662）

5 个 epoch 就超过修复前 50 个 epoch 的水平。论文为 U-Net RMSE 0.0182、MFFGCN 0.0150。

### 3.4 同一份旧权重、同一个 split，修前修后对比

上一轮遗留的验证集评估任务（`eval_val.log`）在修复落地之后才跑完，用的是**修复前训练的
旧 checkpoint**、完整 8000 张验证集：

| 评估时刻 | 用的数据管线 | val RMSE |
|---|---|---|
| 训练时（每 epoch，60 batch） | 错位 tx | 0.0776 |
| 修复后重评（8000 张全量） | 正确 tx | **0.0193** |

同一份权重、同一个验证集，只是把发射机坐标改对，误差就回到论文水平。

**这条证据的额外价值**：旧 checkpoint 本身没坏，只是被错误的坐标评估了。
47 个历史 run 不需要全部重训，用修好的管线重新评估一遍就能救回大部分数字
（注意它们的 `obs_on_signal=True`，协议仍与论文不同，只能作内部对照）。

## 四、影响面：以下数字全部作废

## 七、Setup 4/5 口径校正 + 多种子补跑（11-04 下午）

### 7.1 Setup 4 / 5 改成论文的"采样密度"口径

论文原文：

> Setup 4: In this setup, we **sample the radio map at a random ratio from 1% to 10%**
> in each region, and the sparse observations are uniformly distributed.
> Setup 5: We divide the radio map into two sides randomly. Then, we sample
> **1% of observations from one side and 10% from the other side**.

即 1%–10% 是**观测密度（占像素数的比例）**，不是被遮挡的面积。
原实现（`restricted_area_map` / `restricted_two_sides`）挖掉 1%–10% 面积的矩形，
物理含义完全不同，已按论文重写：

- `s4`：全图保留，`n_obs = round(U(1%,10%) × 65536)`，即 655–6554 个观测点；
- `s5`：随机沿某一轴切成两个半边，一边 1% 密度、另一边 10% 密度（哪边拿哪个随机）；
- 原来那个 `restricted_two_sides` 已删除，换成 `two_side_densities`。

**回归验证**（`src/check_s45.py`，旧文件 `dataset.py.bak.txfix_1104` 并排加载对比）：

| setup | 旧实现观测数 | 新实现观测数 | 结论 |
|---|---|---|---|
| s1 | 284,255,215,257,50 | 完全一致 | 无回归 |
| s2 | 191,168,82,278,23 | 完全一致 | 无回归 |
| s3 | 271,261,123,201,198 | 完全一致 | 无回归 |
| s4 | 挖掉 1%–10% 面积 | 691–6356 个点（均值 3261） | 符合论文 |
| s5 | 挖掉两条边 | 上/下半边精确 10.0% / 1.0% | 符合论文 |

Setup 1–3 的观测掩码与旧代码逐样本完全相同，说明这次改动只影响 s4/s5。

### 7.2 补 4 个种子（seed 1–4）

论文："The experiments are repeated five times with different random seeds,
and we report the mean ± standard deviation across these runs."
因此 `single` 与 `mffgcn(softmax)` 各补齐 seed 1–4，与已有的 seed 0 一起构成 5 种子。

调度改成共享工作队列 `queue.sh`：每个 spec 用 `mkdir runs/.claim_<tag>`
原子抢占，多张卡起多个 worker 不会重复跑同一 tag，空闲的卡会自动接下一单。
列表按"耗时长的排前面"，mffgcn 在前、single 在后。

### 7.3 集群（ivsn）这次用不了

原本打算把 8 个种子作业丢到研究院集群（21×A100-40G）并行跑，实测不可行：

- 每台节点的 `AllocTRES` 都显示 `gres/gpu` 已被占满（node3 5/5、node4 8/8、
  node5 6/6、node7 8/8）；
- 而 `squeue` 里除了本账号两个 PENDING 的残留 smoke 作业外**没有任何运行中的作业**；
- 作业一直是 `Reason=Priority`，即调度器认为"没有空闲卡"。

结论：**GRES 记账漂移**（门户侧跑的任务不在这套 Slurm 里登记，或历史作业异常退出没释放）。
这需要管理员介入，账号侧无法绕过。残留的 22927 / 22930 已 `scancel`。
